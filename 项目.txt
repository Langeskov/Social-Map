你现在要负责设计并实现一个本地优先的人际关系分析桌面应用。

项目暂定名称：

Relationship Intelligence System

中文可以理解为：

个人关系知识库 / 人际关系分析系统 / Relationship Intelligence

--------------------------------------------------
一、项目定位
--------------------------------------------------

这个程序不是传统通讯录，也不是简单的 CRM，更不是只有一个“大模型总结人物”的 AI Chat UI。

核心定位是：

“以人物为节点，以关系为结构，以事件为时间轴，以证据为事实基础，以大模型为分析层的个人关系知识库。”

核心数据链路：

Person
  ↓
Relationship
  ↓
Event
  ↓
Evidence
  ↓
Analysis

系统最终应该能够回答：

- 这个人是谁？
- 我和这个人的关系是什么？
- 我和这个人的关系是如何变化的？
- 过去发生过哪些关键事件？
- 哪些结论有证据？
- 哪些只是用户观察？
- 哪些属于 AI 推断？
- 最近一段时间关系发生了什么变化？
- AI 是根据哪些事件和证据得出结论的？

必须始终保持：

事实 ≠ 用户观察 ≠ AI 推断

AI 推断不能直接成为数据库事实。

--------------------------------------------------
二、设计参考方向
--------------------------------------------------

视觉和交互方向参考以下作品所体现的信息组织方式：

- 《看门狗》系列：人物信息、关系网络、事件信息集中展示
- 《疑犯追踪》：人物节点、关系网络、行为与事件分析
- 《西部世界》：人物档案、行为轨迹、状态分析

可以参考其“情报工作台”的概念，但：

1. 不要直接复制其 UI
2. 不要做成影视作品式的纯装饰界面
3. 不要第一版加入大量动画
4. 第一阶段优先保证数据模型、功能和稳定性
5. 后续再逐步加入高级 UI/UX、动态关系图、视觉化效果

最终方向应该是：

“一个真正可长期使用的人际关系情报工作台”

而不是：

“看起来很酷但实际只能展示假数据的黑客界面”。

--------------------------------------------------
十三、Evidence
--------------------------------------------------

Evidence 是事实来源。

事件和证据必须分离：

Event
├── Evidence
├── Evidence
└── Evidence

例如：

Event：
2026-09-28 对方主动联系

Evidence：
- 聊天截图
- 聊天文本
- 用户手工记录

Evidence 至少包括：

id
event_id
type
title
content
media_id
source_id
captured_at
sha256
metadata
created_at

必须允许用户查看：

“这个分析结论来自哪些事件？”

以及：

“这个事件有哪些原始证据？”

必须建立：

Analysis
↓
AnalysisSource
↓
Event
↓
Evidence

这样的可追溯关系。

--------------------------------------------------
十四、事实 / 观察 / 推断
--------------------------------------------------

这是整个系统的重要原则。

必须明确区分：

Fact
Observation
Inference

例如：

Fact：

“2026-09-28 19:30，对方主动发送消息。”

Observation：

“我感觉最近她的回复速度比以前快。”

Inference：

“根据最近 5 次互动，可能说明互动意愿有所增加。”

不要把三者混成一个文本字段。

AI 默认只能生成：

Observation / Inference

不能直接修改 Fact。

--------------------------------------------------
十五、Analysis
--------------------------------------------------

AI 分析必须是“运行记录”，而不是简单覆盖一个文本字段。

建议：

AnalysisRun

包括：

id
analysis_type
target_type
target_id
model_provider
model_name
prompt_template
context_snapshot
result
created_at
duration

每一次分析都必须保留。

例如：

Analysis #42
Target: Person A
Model: xxx
Context: 最近 30 天
Events: 17
Evidence: 31
Result: ...

以后允许查看：

Analysis #42
Analysis #43
Analysis #44

而不是只保留最后一次结果。

--------------------------------------------------
十六、AnalysisSource
--------------------------------------------------

分析必须能够知道：

“模型看了什么资料？”

AnalysisSource 可以关联：

- Person
- Relationship
- Event
- Evidence
- Memory

这样用户可以追溯 AI 判断依据。

不要只保存最终文本。

--------------------------------------------------
十七、Context Builder
--------------------------------------------------

AI 不允许直接把整个数据库 dump 后发送给模型。

必须有：

ContextBuilder

流程：

Person
↓
Relationship
↓
Relevant Events
↓
Relevant Evidence
↓
Previous Analysis
↓
Memory
↓
ContextBuilder
↓
PromptBuilder
↓
LLM

ContextBuilder 必须允许控制上下文范围。

例如：

最近 7 天
最近 30 天
最近 90 天
全部历史
自定义事件
指定事件

未来可以让 UI 选择：

☑ 基础人物信息
☑ 最近 30 天事件
☑ 关系历史
☑ 用户观察
☐ 更早历史
☐ 其他人物关系

这样可以控制 token 和分析范围。

--------------------------------------------------
十八、AI 分析类型
--------------------------------------------------

至少预留：

PersonAnalysis
RelationshipAnalysis
TimelineAnalysis
EventAnalysis
TrendAnalysis

例如：

人物分析：

“基于已有事实和事件，分析这个人物近期表现出的行为特征。”

关系分析：

“分析我与该人物之间的关系和最近变化。”

趋势分析：

“比较过去 30 天和之前 30 天的互动变化。”

必须避免 AI 产生绝对化结论。

不要输出：

“这个人就是如何如何。”

更合理的是：

“根据已有记录，可以观察到……”

“可能说明……”

“证据不足以确认……”

AI 推断必须和事实区分。

--------------------------------------------------
十九、Memory
--------------------------------------------------

Memory 不等于 Analysis。

Analysis：

“AI 这次分析得出的结论。”

Memory：

“用户明确允许系统长期记忆的信息。”

例如：

“张三喜欢摄影。”

如果只是 AI 猜测，不得直接成为 Memory。

建议：

Memory
├── content
├── type
├── source
├── confidence
├── created_at
├── last_verified_at
└── status

以后由用户确认后再进入长期上下文。

三十九、遇到架构问题时
--------------------------------------------------

不要机械执行。

- SQLite 方案存在不可忽略的问题
- LLM Provider 抽象设计不合理

方案 A
方案 B
影响
推荐原因

不要为了“完成代码”强行选择一个隐藏起来。

如果只是普通实现细节，则直接实现。

如果属于架构级决策，则在代码之前说明。
